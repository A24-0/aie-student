# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Датасет: `S12-hw-dataset.csv`, прогнозируется столбец `target` по времени.
- Разбиение: последовательный `train / validation / test` по времени (без random split).
- Сравнивались B1 (naive-last), B2 (moving average), B3 (Ridge на лагах/rolling/календаре), R1 (GRU).
- Лучший подход выбирался по минимальному **val MAE** (см. `artifacts/runs.csv`); на **test** оценка один раз для выбранной модели.

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: `target`
- Частота временного ряда: по колонке `date` (часовые метки в предоставленном файле).
- Горизонт прогноза: 1 шаг вперёд.
- Размер датасета и диапазон дат: см. sanity-check в ноутбуке.

- Комментарий: ряд нестационарен по смыслу временных рядов; важны тренд и локальная сезонность; random split недопустим из-за автокорреляции и утечки «будущего».

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: три последовательных отрезка времени после сортировки по `date`.
- Какие доли или интервалы использовались: ~70% / 15% / 15% (реализация в ноутбуке).
- Почему `random split` здесь некорректен: перемешивание нарушает временной порядок и даёт нереалистично оптимистичные метрики; возможна утечка будущих значений в признаки.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: `lag_1`, `lag_7`, `lag_14`.
- Какие rolling-признаки использовались: `rolling_mean_7`, `rolling_std_7` (без утечки из будущего).
- Какие календарные признаки использовались: день недели (`dow`).
- Как обрабатывались пропуски после построения лагов/rolling: строки с NaN удаляются в соответствующих сплитах.
- Использовалось ли масштабирование и где именно оно обучалось: `StandardScaler` для табличных признаков B3 — **fit только на train**.

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:

- B1 (`naive-last`): прогноз = последнее наблюдённое значение ряда.
- B2 (`moving-average`): среднее по окну прошлых наблюдений (размер окна в ноутбуке, напр. 24).
- B3 (`ridge-lag-features`): Ridge на лагах, rolling и календарных признаках.
- R1 (`gru-forecast`): GRU на скользящих окнах нормированного ряда (`window_size` в конфиге).

Дополнительно:

- Основная метрика выбора лучшей модели: минимальный **val MAE** (явно зафиксировано в ноутбуке и `runs.csv`).
- Дополнительные метрики: RMSE, MAPE на val и test.
- `window_size` для `GRU`: см. `best_gru_config.json` (например, 48).
- Batch size: см. ноутбук.
- Максимальное число эпох: см. ноутбук (GRU).
- Optimizer: Adam для GRU.
- Learning rate: см. ноутбук.
- Как сохранялась лучшая модель: `state_dict` лучшей по val MSE эпохи в `artifacts/best_gru.pt`.

## 7. Анализ

Наивный baseline задаёт опорный уровень ошибки. Скользящее среднее сглаживает шум, но отстаёт при резких изменениях. Ridge на лагах и сезонных признаках использует линейную структуру ряда. GRU улавливает нелинейные паттерны в окне; при малом объёме данных она может переобучаться или не превзойти Ridge — смотреть на конкретные метрики. Утечки возможны при неправильном shift признаков; выбор по val, а не по test, обязателен.

Для временных рядов сначала — корректный temporal split и простые baseline, затем линейные модели на признаках и при необходимости GRU. Главное — не смешивать прошлое и будущее в признаках и метриках.
